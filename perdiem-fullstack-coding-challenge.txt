Full-Stack Engineering Take-Home
Role: Full-Stack Engineer (React Native / Web + Node.js / TypeScript) Time budget: 4–6 hours. If you blow past that, stop and write down what you'd do next. Stack you'll touch: TypeScript, React Native or Next.js, a thin Node backend, Square's Catalog & Locations APIs.


________________


Why this challenge
At Per Diem we power mobile ordering and loyalty and Square is the POS we integrate with most deeply. Almost every feature we ship has to answer the same three questions:


1. What does this brand sell? (Catalog)
2. Where can they sell it? (Locations)
3. Right now, can a guest actually buy it? (Availability — by location, day, and time)


This challenge is a tiny version of that real work. We're not looking for a finished product  we're looking for how you think, how you handle ambiguity, and what your code looks like when nobody's watching.


________________


The challenge
Build a small multi-location menu browser on top of Square's APIs.


Pick one of:


* 📱 React Native app (Don’t use expo), or
* 🌐 Web app (Next.js, Remix, or your framework of choice)


Either path is judged equally — pick what you're strongest in.
Core requirements
#
	Requirement
	1
	Fetch locations from Square's Locations API and render a location switcher.
	2
	Fetch catalog items and categories from Square's Catalog API.
	3
	When the user picks a location, only show items actually available at that location. (Hint: look at present_at_all_locations, present_at_location_ids, absent_at_location_ids.)
	4
	Group items by category and let the user filter by category.
	5
	Tapping an item shows a detail view with name, description, image, and price formatted correctly (Square returns money in the smallest currency unit — cents).
	6
	Real loading, empty, and error states. No bare spinners that spin forever.
	Bonus — pick whichever excite you
These are what separates strong candidates. Quality over quantity — one bonus done well beats four done sloppily.


* ⭐ Time-of-day & day-of-week availability (the one we care about most) Some items only exist for breakfast, weekends, or happy hour. Use Square's category availability / menu features to filter items that aren't currently orderable in the selected location's local timezone. Out-of-window items should be hidden or visibly disabled.


Heads up: Square's APIs around scheduled menu availability have evolved — part of the challenge is reading their docs and choosing a sensible approach. Document what you picked and why.


* Modifiers — render item modifier lists on the detail screen.
* Search — full-text search across the visible menu.
* Cart — add items to a cart and compute a subtotal. No payment integration required.
* Out-of-stock — surface inventory state using Square's Inventory API.
* Offline-friendly — cache the catalog so the menu still loads briefly without a network.

Technical guardrails
These are non-negotiable — they reflect how we ship code at Per Diem.


* ✅ TypeScript everywhere, with real types at every boundary. We don't want to see any, // @ts-ignore, or types that lie.
* ✅ All Square API calls go through your own backend (Node, a Next.js route handler, an Expo API route, a serverless function — your call). The client must never see a Square access token.
* ✅ Secrets in .env, never committed. Include a .env.example.
* ✅ Comment the why, not the what. Trade-offs, edge cases, and assumptions belong in comments.
* ✅ Sensible error handling. Square will rate-limit you, return partial pages, and occasionally hand you weird shapes — handle it.
* ✅ A README that covers:
   * How to run it locally
   * How to set up a Square sandbox + seed data
   * Your architectural decisions and the trade-offs you made
   * What you'd build next given another week

How we evaluate
We grade on five dimensions, weighted roughly equally:


1. Correctness — Does the location filter actually filter? Are prices right? Does category availability behave the way a guest would expect?
2. Code quality — Folder structure, typing, naming, separation of concerns, no dead code.
3. Security — Secrets handling, input validation, no tokens shipped to the client, no SSRF foot-guns.
4. Product judgment — Does this feel like something a real guest could use? Are empty/error states thought through?
5. Communication — README, commit history, code comments, and the Loom walkthrough.
What we are not grading on
* Pixel-perfect visual design (clean & usable is enough).
* 100% test coverage (a few well-chosen tests > a wall of trivial ones).
* Completing every bonus.
* Speed of submission.

Setup pointers
1. Create a free Square developer account → developer.squareup.com
2. Create a sandbox application and grab the access token + sandbox base URL.
3. Either use Square's seed data, or seed your own — aim for 2 locations, 3–4 categories, and 6–10 items, with at least one item that's only available at one of the two locations. (For the time/day bonus, set up at least one category with limited hours.)
4. Useful docs:
   * Catalog API → https://developer.squareup.com/reference/square/catalog-api
   * Locations API → https://developer.squareup.com/reference/square/locations-api
   * Square Node SDK → https://www.npmjs.com/package/square

FAQ
Can I use AI tools (Copilot, Claude, Cursor)? Yes — we use them daily. The expectation is that you understand and can defend every line in your repo.


Can I use UI libraries? Absolutely. Tailwind, shadcn/ui, NativeWind, NativeBase, Tamagui — your call.


Do I need a database? No. In-memory or simple caching is fine for this scope.


What if I find a Square API limitation while doing the bonus? Document it in the README, propose a workaround, and move on. Knowing when to stop is part of the job.


Can I ask questions during the challenge? Yes. Ambiguity is part of the work — but if something is genuinely blocking, email us. We'd rather you ask than spin.
